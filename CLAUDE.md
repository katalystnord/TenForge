# THE TEN TENETS

**Settled by David, 2026-11-12** (adapted from SurView's tenets,
2026-07-21). Everything else in this file is subordinate to them; where
the rest of the file disagrees with a tenet, the tenet wins.

1. **Force, displacement and images in, trustworthy results out.** Two
   co-equal pillars: faithfully record the test, and analyse it by named
   standard procedures. Everything else may only augment them.
2. **There was no open, hardware-agnostic, ecosystem-native testing
   application a working scientist could adopt.** This is why TenForge
   exists.
3. **We build our own analysis core from the standards' definitions.**
   Existing code is a source of ideas, not a parent.
4. **We incorporate vetted good solutions** from wherever they come.
5. **We hold no allegiance to any upstream or rig at the code level**:
   licensing and attribution only.
6. **All interoperability with other tools happens at the file level**,
   never at the model or code level.
7. **The GUI is also the product.** A UX defect is a defect.
8. **We break with inherited approaches** whenever that is required.
9. **We quantify and report reliability**: calibration class,
   uncertainty, and whether each result is to the standard or only
   aligned with it.
10. **We keep the record pristine with retained provenance**: raw counts,
    device timestamps, no silent loss, conversion or resampling.

## Settled decisions

- **Software, for any machine.** No rig is a first-class target. Fixtures
  and rigs are data the software records, not things this project designs.
- **Scope:** tension, compression, bending (three- and four-point). Later:
  fracture toughness, small punch. Concrete is out of scope.
- **Independent kits.** SurView, OpenCorr and TenForge never link, import
  or build against each other's code. Each installs, runs and is useful
  alone. Interop is optional at both ends, through open documented file
  formats that any third party can also use. TenForge never calls,
  launches or detects another tool; the user hands files across. Each
  kit's tests run with the others absent.
- **Klipper** is the machine-side firmware of choice for DIY rigs, talked
  to through Moonraker as a separate process. Its GPL stays on its side.
- **Stack:** C++20, Qt 6 for the shell, VTK for everything drawn and for
  field data, Eigen for numerics, CMake. **Qt Charts and Qt Quick 3D are
  off-limits** (GPL-3.0-only); charts go through `vtkChartXY`.
- **`tf_analysis` has no Qt.** Pure functions over arrays, Eigen only. A
  configure-time check and a test that compiles every public header with
  no Qt on the include path enforce it.
- **Standards:** profile parameters carry their source and a confirmed or
  unconfirmed flag. Every standard is treated alike, whichever body
  issued it; profiles hold parameters and clause references, never text.
- **Attribution** goes in README and NOTICE, never the About dialog
  (`katalystnord/policy-on-attribution.md`). Datasets follow
  `katalystnord/policy-on-training-and-extraction.md`.

## How this project is run

SurView's regime, carried over deliberately (David, 2026-08-18).

### The one command

```bash
tools/run-tests.sh
```

Builds and runs the whole suite. Walkthrough tests carry their own X
server (`xvfb-run`, wired in `tests/CMakeLists.txt`), so `ctest` is
headless however it is started.

### The order things happen in

1. **A failing test first**, named for the CASE, not the function.
2. **Then the code**, written so it can be covered: pure functions taking
   values and returning values, separated from widgets, threads, files and
   devices.
3. **Then the full suite.**
4. **Then commit.** Not before.

### What a green test is worth

- A green test proves nothing until it has been shown to fail WITHOUT the
  fix. Record the negative check in the test file, including what it did
  not catch.
- A comment may say WHY. It may not assert what the design requires unless
  a test of that name enforces it.
- A walkthrough test may only do what something on screen tells it to do.
- A test must not re-derive the arithmetic it is testing.
- Fixtures are committed, never generated by the code under test, each with
  an independently verified property, lopsided in every axis the code could
  confuse.

### No em-dashes, ever

Enforced by `tools/check-no-em-dashes.sh` in the pre-commit hook and first
in CI. Substitutes: `--` in a C++ comment, `-` in user-facing text and
Markdown.

### The hook

```bash
git config core.hooksPath tools/git-hooks      # once per clone
```

Refuses a commit touching C++ or CMake that does not build and pass.

## Layout

```
src/analysis/   tf_analysis  standards engine, Eigen only, no Qt
src/core/       tf_core      record, profiles, calibration, sequencer, drivers API
src/gui/        tf_gui       the application window
src/cli/        tf-analyse   headless command line
tests/          one executable per subject
docs/specs/     the file contracts: test record, profile, results
tools/          run-tests.sh, check-no-em-dashes.sh, sanitize.sh, git-hooks/
```

Driver plugins (`src/drivers/`) arrive in Phase 5, not before: no empty
targets (engineering principle 7).
